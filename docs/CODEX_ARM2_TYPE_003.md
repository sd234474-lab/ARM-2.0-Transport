## Предметные основания из Единой конфигурации ARM 2.0
Лист `03 Конфигурация` [ARM 2.0](https://docs.google.com/spreadsheets/d/1jxj_ATB7pfgdbukaQ5mH2CdsPPisDAxU5ggitO2pPjI/edit):
- `DISC-TYPE-01` (08.11.2026): один неизменяемый `TYPE-000001`, не заменять и не выдавать новый при редактировании.
- `DISC-TYPE-03`: обязательное имя; крайние пробелы убираются; полностью одинаковые имена запрещены даже при переименовании; поиск дубля гарантирует UNIQUE БД.
- `DISC-TYPE-04/05/06/07`: только автоматические REVIEW/CONFIRMED, `False` у тарировки/Wialon — заполнено, `None` — не заполнено; СТС по действующему предметному правилу `True` либо `None` для незавершённого описания, но явный `False` запрещён.
- `DISC-TYPE-09`, `VER.R01`: версия начинается с 1, увеличивается при успешном изменении; сохранение с устаревшей версией отклонять без перезаписи данных другого оператора; не показывать версию в карточке.
- `HIST.R01`, `DISC-TYPE-08`: единый журнал истории разных справочников с автором, источником, датой и изменениями `было→стало`, без отдельных журналов в карточках; историю загружать только по запросу. **Механизм общего журнала ещё не готов.** Поэтому в данном пакете НЕ вводить пользовательские write-API и НЕ считать внутреннее редактирование готовым для эксплуатации.
- `DISC-TM-10` (виды работ) и `DISC-DEL-01` (удаление) не завершены; не внедрять.
- Ошибки Transport MAX, в частности `0055_image_limits.py`, не исправлять.

## Цель одного пакета
Добавить только **внутреннюю сервисную операцию редактирования существующего типа** с защитой версий. Это промежуточный код, не вызываемый пользователями до реализации единого журнала истории. Никаких новых таблиц, миграций, HTTP-эндпоинтов, UI и дополнительных предметных полей.

## Точное поведение
1. В `backend/app/arm2/vehicle_type_store.py` реализуй `update_vehicle_type(db: Session, type_id: str, expected_version: int, name: str, requires_sts: bool | None, requires_calibration: bool | None, requires_wialon: bool | None) -> VehicleType` (или эквивалентную точную сигнатуру).
2. Одна операция заменяет утверждённые редактируемые поля полной переданной формой. Обязательна проверка `expected_version` как положительного целого, не bool, до изменения записи.
3. Получить строку `VehicleType` по `id` с `SELECT ... FOR UPDATE` внутри транзакции; если строки нет — отдельное предметное исключение NotFound. Сравнить `row.version` и `expected_version` **под блокировкой**. При несовпадении — отдельное Conflict исключение, данные не менять, не выполнять commit.
4. Выполнить существующие `normalize_type_name`, `normalize_type_requirements`, `type_status` из `vehicle_type_rules.py`. Повторно не изобретать расчёт статуса; для СТС=False ошибка.
5. Если хотя бы одно из предметных полей действительно изменилось, присвоить поля, обновить status, увеличить version ровно на 1 и сделать `flush`; транзакцией/commit управляет вызывающая сторона. Если вся переданная форма совпадает с текущей, version не увеличивать (отсутствие изменения — не «успешное изменение»). Обозначить эту границу явно.
6. При повторном имени получить UNIQUE-конфликт БД; транзакция откатывается снаружи, исходные данные и ID сохраняются.
7. Никогда не менять ID и не создавать новый TYPE при переименовании. Не задействовать `next_id` в UPDATE.
8. Не принимать/не записывать поля code, details, source, created_at, архивность, user_id или историю через этот метод; автор и происхождение должны оформляться **в общем журнале при будущей публикации операции**.
9. Оставить существующий `create_vehicle_type` неизменным по поведению.
