Лист `03 Конфигурация` в https://docs.google.com/spreadsheets/d/1jxj_ATB7pfgdbukaQ5mH2CdsPPisDAxU5ggitO2pPjI/edit :
- `DISC-TYPE-01`, редакция 08.11.2026: ID каждого типа техники = **`TYPE-000001`** и далее, отдельная последовательность, неизменяемый единственный предметный ключ без параллельного UUID.
- `ID.R01`: ID выдаётся автоматически, не повторяется после удаления/отката, не зависит от названия/бизнес-кода; правило префиксов `VEH` и `TYPE`.
- `DISC-TYPE-03`: название обязательно, свободное, по краям обрезаются пробелы; **полностью одинаковые нормализованные названия** для двух типов запрещены; можно переименовывать без изменения ID. Не изобретать `casefold`, принудительное изменение регистра или дополнительную максимальную длину.
- `DISC-TYPE-04/05/06/07`: поля `requires_sts`, `requires_calibration`, `requires_wialon`; `False` — явно заполненное значение; отсутствие = `None` => REVIEW. СТС по умолчанию True, False недопустимо в действующей предметной модели. Если все три ответа заполнены и имя непустое => CONFIRMED, иначе REVIEW. Не рассчитывать готовность конкретных машин.
- `DISC-TYPE-09`, `VER.R01`: системная версия при создании = 1; в дальнейшей операции обновления должна увеличиваться, с защитой от конкурентных правок. **Полное редактирование/HTTP UI — не в этом пакете.**
- `HIST.R01` и `DISC-TYPE-08`: универсальный журнал должен регистрировать происхождение создания с автором; механизм общего журнала ещё отдельный пакет. НЕ вводить в модель TYPE отдельные `source`/`created_at` как замену истории; в этом пакете разрешена только изолированная тестовая запись без пользовательского API.
- `DISC-TYPE-02` и `DISC-TM-10` ещё открыты: не добавлять бизнес-код `code`, связи с видами работ, импорт анкеты или допуск.
- Данные ARM 1.0 НЕ мигрировать, старые файлы `contractor*` не переносить.

## Одна задача
Добавить **постоянное хранение** нового справочника типов в отдельной таблице ARM 2.0 и внутренний строго контролируемый метод **создания** записи. Без редактора, списка, интерфейса и HTTP-эндпоинтов.

### Обязательные результаты
1. Миграция `0057` после `0056` создаёт отдельный PostgreSQL sequence `arm2_vehicle_type_id_seq` для TYPE и таблицу `arm2_vehicle_types`.
2. Поля таблицы:
   - `id` — строковый PRIMARY KEY `TYPE-000001` и далее, **никаких UUID или второго авто-ID**;
   - `name` — нормализованное непустое строковое имя и UNIQUE;
   - `requires_sts` — булево либо NULL, с server default TRUE, False запрещено даже при обходе сервиса;
   - `requires_calibration`, `requires_wialon` — nullable bool, отсутствие не превращать в False;
   - `status` — `REVIEW` или `CONFIRMED`, вычисленный сервисом на основе уже утверждённых правил;
   - `version` — целое системное число, начально 1.
   В миграции ограничить статус и nonempty имя, и согласовать SQLAlchemy ORM-класс с физическими типами/ограничениями. Не создавать `code`, `source`, `details`, дополнительные исторические поля или архивность.
3. Обновить `backend/app/arm2/ids.py`: добавить только утверждённый `TYPE` в фиксированную карту sequences; прежний `VEH` не изменять.
4. Добавить ORM-модель, использующую существующий `Base` в `backend/app/db.py`; импортировать модель в Alembic metadata минимально, чтобы новые изменения отслеживались в будущих миграциях. Не копировать `models.py` целиком.
5. Добавить внутреннюю функцию `create_vehicle_type(session, name, requires_sts=True, requires_calibration=None, requires_wialon=None)` (параметры или равнозначная структура), вызывающую готовые `normalize_type_name`, `normalize_type_requirements`, `type_status` и `next_id(session,"TYPE")`. ID выдаётся только в процессе создания; функция **не делает commit сама** — транзакция управляется вызывающей стороной; `flush` для выявления конфликта UNIQUE. Не делать повторный запрос/повторную попытку создания с новым ID при конфликте имени.
6. Объект должен сохраняться только с постоянным ID и вычисленным status, без права вручную подменять статус через этот метод. Дополнительное изменение состояния в общем API отсутствует.
