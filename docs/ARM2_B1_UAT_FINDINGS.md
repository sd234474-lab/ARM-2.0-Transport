## B1-UAT-001 — Валидация госномера по TYPE-ID

**Дата выявления:** 14.11.2026  
**Модуль:** ARM 2.0 / справочники TYPE и VEH / создание и изменение машины  
**Статус:** `РЕШЕНИЕ ВЛАДЕЛЬЦА` (предметное решение принято, реализация и повторный тест не выполнены)  
**DOC-036:** `VEH.F03`, `VEH.F04`, `DISC-TYPE-04`, `DISC-TYPE-13` (новое требование), листы 03/08/10/15.  
**Исходная реализация:** [vehicle_store.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_store.py), [vehicle_type_models.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_type_models.py), [vehicle_models.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_models.py).

### Наблюдение / воспроизведение

В форме «Машина: создание» введён `Е584ПР186`. Сохранение отклонено сообщением «Государственный номер: неверный формат», поскольку буква `П` не входит в установленный набор `АВЕКМНОРСТУХ`. Это корректное отклонение по **существующему** `VEH.F03`, не отдельный дефект.

В ходе анализа обнаружено, что сервер принимает **оба** шаблона для любой машины независимо от `type_id`:

- автомобиль: `А123ВС186` (одна буква, три цифры, две буквы, 2–3 цифры региона);
- самоходная машина: `1234АВ86` (четыре цифры, две буквы, две цифры региона).

Сейчас это соответствует прежнему общему правилу, но не контролирует соответствие выбранному типу техники.

### Утверждённое владельцем изменение предметной модели

1. В **существующий справочник TYPE** добавить отдельное видимое поле/колонку **«Тип государственного номера»** с двумя значениями: **«Автомобильный»** / **«Самоходная техника»**.
2. Значение привязано к **постоянному TYPE-ID**, а не выводится из текста имени типа («Самосвал», «Трактор» и т. п.). Оператор указывает категорию конкретного TYPE; примеры не являются автоматическими классификаторами.
3. При создании и изменении VEH с назначенным TYPE сервер должен применять только шаблон номера, соответствующий категории этого TYPE; не принимать номер второй категории просто потому, что он удовлетворяет общему regex.
4. При изменении `type_id` машины повторно проверить совместимость её госномера с категорией вновь выбранного TYPE; не сохранять несовместимую пару, объяснить ожидаемый формат.
5. Существующие правила VEH.F03 о допустимых буквах, однозначных латинских двойниках, нормализации и уникальности **сохраняются**. Не менять их незаметно.
6. Тип без заполненной категории номера считать неполно описанным (REVIEW), в согласовании с уже действующей методикой полноты TYPE; предметное поведение существующих типов при миграции требуется отдельно определить.

### Первоначально открытые вопросы (решения по пунктам 1–3 см. ниже)

- **Существующие TYPE:** как заполнить новую категорию, не угадывая по имени, не нарушая текущие связи и статусы; возможны REVIEW и ручное подтверждение.
- **Изменение категории ранее использованного TYPE:** как выявлять связанные VEH с номерами, не соответствующими новому шаблону, и блокировать небезопасную смену; без автоматической переделки госномеров.
- **VEH без назначенного TYPE:** такая запись допускается по VEH.F04 и импорту IMP2.VEH-01; уточнить, применяется ли временно общая проверка двух форматов до выбора TYPE или другая утверждённая процедура. Не запрещать существующий сценарий без отдельного решения.
- **Права, API, миграции, интерфейс:** точное имя физического поля/кода, UI селектора TYPE, совместимость с формами и импортом, автоматические тесты. Эти элементы — задачи технического проектирования, не разрешение на coding.
- **Существующие данные и регрессия:** проверить сохранность ID/связей/истории и недопустимость новых дубликатов при миграции.
- Влияние на табличный и анкетный импорт (в т. ч. правило UAT-014 по удалению пробелов) должно быть адресно проверено, но не изменено автоматически.

### Решения владельца по трём переходным случаям — 14.11.2026

**УТВЕРЖДЕНО ВЛАДЕЛЬЦЕМ** после сверки B1-UAT-001 с DOC-036:

1. **Существующие TYPE:** новое поле «Тип государственного номера» у ранее созданных типов оставить пустым до заполнения оператором. Если значение не заполнено, полнота описания типа — `REVIEW`; автоматически выводить категорию из имени типа запрещено. Связи и записи VEH сохранять, не удалять.
2. **Изменение категории у используемого TYPE:** если после изменения категории хотя бы одна связанная машина имеет несовместимый госномер, **запретить сохранение изменения категории** до устранения несоответствий. Не исправлять госномера автоматически.
3. **VEH без TYPE:** разрешить создание и хранение без назначенного TYPE-ID. До назначения типа проверять госномер по **любому из двух** форматов VEH.F03; после назначения TYPE проверять исключительно шаблон категории выбранного TYPE-ID.

**Предметные вопросы 1–3 закрыты.** Технические аспекты (схема/миграция, безопасная проверка связанных VEH, API, UX ошибок, импорт, атомарность и тесты) остаются для проектирования единого ТЗ. Статус `РЕШЕНИЕ ВЛАДЕЛЬЦА`; код не изменялся и новая логика не проверялась.

### Критерии для будущего ТЗ и повторной UAT-проверки

Проверить создание TYPE с обеими категориями; совместимые и несовместимые номера для каждого TYPE; смену TYPE у VEH; пустую категорию/REVIEW; номер с латинскими двойниками; уникальность; сохранность неизменных полей/версии/истории; миграционную совместимость и случай VEH без TYPE после отдельного решения. Обязательна серверная проверка, не только подсказка фронтенда.

**Текущий итог:** решение о привязке валидации к TYPE-ID принято; код не менялся, тесты новой логики не выполнялись.

## B1-UAT-002 — Компоновка стартового экрана справочника техники

**Дата выявления/согласования владельцем:** 14.11.2026  
**Экран:** ARM 2.0 → справочники → «Техника» (стартовый экран и таблица).  
**Статус:** `РЕШЕНИЕ ВЛАДЕЛЬЦА` — включить в будущую единую задачу Codex после завершения просмотра B1; код не изменён.  
**Основание:** сопоставление двух скриншотов, представленных владельцем в ходе ручной Ubuntu UAT: текущий ARM 2.0 (первый скриншот) и первый прототип (второй скриншот).  
**Связь с конфигурацией:** UX2.VEH-01; при формировании ТЗ сверить действующую DOC-036/03 и не подменять ею этот визуальный протокол.

### Что увидели (текущий ARM 2.0)

- Верхний ряд плашек разделов несимметричен: плашка «Техника» непропорционально шире соседних, поскольку в неё встроены ссылки «Техника», «Типы техники», «Согласование с заказчиком».
- Ссылки на подразделы смешаны с навигацией верхнего уровня, что затрудняет визуальное восприятие.
- Кнопка «+ Новая запись» находится слева возле заголовка списка, а не отдельно справа.
- В показанном B1 нет отдельной строки навигационного пути («хлебных крошек»), которая присутствует в прототипе.
- В прототипе показаны плашки-счётчики состояния; там они неудобно переносятся на вторую строку. Требуется единая линия счётчиков при достаточной ширине экрана. **Важно:** на скриншоте B1 соответствующие счётчики не показаны; не считать наличие всех механизмов их расчёта доказанным.

### Что меняем — утверждённое владельцем

1. Верхний уровень навигации представить **плашками одинаковой ширины/высоты с симметричным расположением** в один ряд на доступной ширине; внутренние ссылки не увеличивают размер отдельной плашки.
2. Разделить уровни навигации: **плашки основных разделов сверху**, ниже — **отдельная горизонтальная строка подразделов активного раздела** («Техника», «Типы техники», «Согласование с заказчиком»). Недоступные подразделы не выдавать за действующие.
3. Ниже строки подразделов показать **навигационный путь / хлебные крошки**, позволяющий ориентироваться и переходить по доступным уровням.
4. Плашки показателей/счётчиков разместить **одной строкой на широком экране**, не разбивая без нужды на две строки; их фактическое наличие, смысл и источники данных проверять отдельно, не создавать фиктивные показатели.
5. Перенести зелёную кнопку **«+ Новая запись» вправо**, отдельно от строки показателей и таблицы, по расположению первого прототипа.

### Что сохраняем

- **Цветовую схему ARM 2.0**, которую владелец оценил выше цветового решения первого прототипа; не копировать бледно-зелёный фон и белые плашки прототипа как обязательный дизайн.
- Действующую компоновку **строк и колонок таблицы техники** в ARM 2.0: кардинальную переработку таблицы не планировать в рамках этого замечания.
- Действующие функции поиска, фильтрации, сортировки, прав доступа и серверного списка; визуальная коррекция не должна менять их предметную семантику.

### Границы и вопросы перед итоговым ТЗ

- Адаптивная компоновка на узких экранах: требование «в один ряд» относится к ширине, где элементы помещаются; на мобильном экране не допускать горизонтального переполнения и ухудшения доступности. Конкретные breakpoints уточняются технически.
- Состав и расчёт счётчиков необходимо сопоставить с утверждёнными требованиями; не реализовывать автоматически показатели из старого прототипа без предметного основания.
- Отделить визуально неактивные разделы («Договоры», «Территории», «Нормативы», «Согласование с заказчиком») от работающей навигации; прежние заглушки не превращать в фиктивные функции.

### Критерии будущей проверки

На широком экране: верхние плашки равны по геометрии и симметричны; подразделы расположены отдельным рядом; путь навигации отображается и работает для доступных уровней; кнопка создания стоит справа; доступные и утверждённые счётчики располагаются в одну строку. Цветовая схема B1 и таблица техники сохранены. На узком экране нет обрезаний, перекрытий или ложных активных ссылок; навигация и ввод остаются доступными.

**Текущий итог:** компоновка согласована владельцем, включена в накопительный перечень. Это не подтверждение завершённой разработки, не готовое ТЗ и не разрешение на изменение кода.

## B1-UAT-003 — Единая кнопка создания записи во всех справочниках

**Дата утверждения владельцем:** 14.11.2026  
**Экраны:** справочники «Техника», «Типы техники», «Собственные организации», «Контрагенты»; правило для всех будущих справочников ARM 2.0.  
**Статус:** `РЕШЕНИЕ ВЛАДЕЛЬЦА`; накопительное замечание текущего B1, **не готовое ТЗ Codex**.  
**Связи:** B1-UAT-002 (общая компоновка справочника техники), DOC-036 / UX2.VEH-01; перед итоговым ТЗ проверить применимость к прочим справочникам и общим UI-компонентам.

### Что увидели

- Действие создания записи отображается неодинаково на разных экранах.
- Для ряда справочников использована надпись «Новая запись», а у «Типов техники» — обычная текстовая ссылка «Создать» без заметного выделения.
- Расположение и оформление действия не унифицированы, из-за чего оператору сложнее быстро найти одинаковую операцию.

### Что меняем — утверждённое владельцем

1. **Единая подпись:** на всех экранах справочников — **«Создать»** с видимым значком **«+»** перед словом; итоговый вид `+ Создать`. Убрать вариант «Новая запись» с этих кнопок.
2. **Единый внешний вид:** заметная **тёмно-зелёная кнопка**, белый текст и плюс; не простая текстовая ссылка, оформление одинаковое во всех справочниках.
3. **Единое расположение:** кнопка находится **справа, в одной строке напротив названия конкретного справочника**, к созданию записи которого относится.
4. **Область применения:** «Техника», «Типы техники», «Собственные организации», «Контрагенты» и все будущие справочники ARM 2.0.
5. **Реализация для будущего ТЗ:** использовать общий переиспользуемый UI-компонент либо единый механизм оформления, чтобы соблюдение правила не зависело от ручной верстки каждого справочника.

### Что сохраняем

- Текущий смысл действия: открыть создание записи соответствующего справочника.
- Действующие права, проверки обязательных полей и серверную логику сохранения; визуальная унификация не должна обходить ограничения доступа.
- Цветовую систему ARM 2.0 в целом, за исключением утверждённого оформления кнопки.
- Таблицы и предметную структуру справочников без дополнительной переделки.

### Связь с B1-UAT-002

Запись **B1-UAT-003 уточняет и заменяет только требования к названию и внешнему виду кнопки** в B1-UAT-002: вместо «+ Новая запись» везде должно быть **«+ Создать»**. Требование B1-UAT-002 расположить действие справа остаётся в силе и теперь распространено на все справочники. Остальная компоновка из B1-UAT-002 не меняется.

### Критерии для будущего ТЗ и повторной UAT-проверки

Во всех четырёх текущих справочниках (и в общем компоненте для новых) отображается одна и та же тёмно-зелёная кнопка **«+ Создать»** с белым текстом справа от названия; она открывает форму создания правильного типа записи. Сохраняется контроль прав (недоступное действие не становится активным). На узких экранах действие не перекрывает заголовок и остаётся доступным; конкретную адаптивную компоновку определить при реализации.

**Текущий итог:** согласовано владельцем и добавлено в перечень замечаний. Код B1 не менялся, исправление и повторная проверка не проводились.
