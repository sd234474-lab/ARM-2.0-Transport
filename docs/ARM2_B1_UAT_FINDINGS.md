## B1-UAT-001 — Валидация госномера по TYPE-ID

**Дата выявления:** 14.11.2026  
**Модуль:** ARM 2.0 / справочники TYPE и VEH / создание и изменение машины  
**Статус:** `РЕШЕНИЕ ВЛАДЕЛЬЦА` (предметное решение принято, реализация и повторный тест не выполнены)  
**DOC-036:** `VEH.F03`, `VEH.F04`, `DISC-TYPE-04`, `DISC-TYPE-13` (новое требование), листы 03/08/10/15.  
**Исходная реализация:** [vehicle_store.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_store.py), [vehicle_type_models.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_type_models.py), [vehicle_models.py](https://github.com/sd234474-lab/ARM-2.0-Transport/blob/aaba19e5c363a8fee22eb6c49060d3452117bcd9/backend/app/arm2/vehicle_models.py).

### Наблюдение / воспроизведение

В форме «Машина: создание» введён `Е584ПР186`. Сохранение отклонено сообщением «Государственный номер: неверный формат», поскольку буква `П` не входит в установленный набор `АВЕКМНОРСТУХ`. Это корректное отклонение по **существующему** `VEH.F03`, не отдельный дефект.

В ходе анализа обнаружено, что сервер принимает **оба** шаблона для любой машины независимо от `type_id`:

- автомобиль: `А123ВС186` (одна буква, три цифры, две буквы, 2–3 цифры региона);
- самоходная машина: `1234АВ86` (четыре цифры, две буквы, две цифры региона).

Сейчас это соответствует прежнему общему правилу, но не контролирует соответствие выбранному типу техники.

### Утверждённое владельцем изменение предметной модели

1. В **существующий справочник TYPE** добавить отдельное видимое поле/колонку **«Тип государственного номера»** с двумя значениями: **«Автомобильный»** / **«Самоходная техника»**.
2. Значение привязано к **постоянному TYPE-ID**, а не выводится из текста имени типа («Самосвал», «Трактор» и т. п.). Оператор указывает категорию конкретного TYPE; примеры не являются автоматическими классификаторами.
3. При создании и изменении VEH с назначенным TYPE сервер должен применять только шаблон номера, соответствующий категории этого TYPE; не принимать номер второй категории просто потому, что он удовлетворяет общему regex.
4. При изменении `type_id` машины повторно проверить совместимость её госномера с категорией вновь выбранного TYPE; не сохранять несовместимую пару, объяснить ожидаемый формат.
5. Существующие правила VEH.F03 о допустимых буквах, однозначных латинских двойниках, нормализации и уникальности **сохраняются**. Не менять их незаметно.
6. Тип без заполненной категории номера считать неполно описанным (REVIEW), в согласовании с уже действующей методикой полноты TYPE; предметное поведение существующих типов при миграции требуется отдельно определить.

### Вопросы, которые НЕ считаются решёнными и должны быть проработаны перед ТЗ

- **Существующие TYPE:** как заполнить новую категорию, не угадывая по имени, не нарушая текущие связи и статусы; возможны REVIEW и ручное подтверждение.
- **Изменение категории ранее использованного TYPE:** как выявлять связанные VEH с номерами, не соответствующими новому шаблону, и блокировать небезопасную смену; без автоматической переделки госномеров.
- **VEH без назначенного TYPE:** такая запись допускается по VEH.F04 и импорту IMP2.VEH-01; уточнить, применяется ли временно общая проверка двух форматов до выбора TYPE или другая утверждённая процедура. Не запрещать существующий сценарий без отдельного решения.
- **Права, API, миграции, интерфейс:** точное имя физического поля/кода, UI селектора TYPE, совместимость с формами и импортом, автоматические тесты. Эти элементы — задачи технического проектирования, не разрешение на coding.
- **Существующие данные и регрессия:** проверить сохранность ID/связей/истории и недопустимость новых дубликатов при миграции.
- Влияние на табличный и анкетный импорт (в т. ч. правило UAT-014 по удалению пробелов) должно быть адресно проверено, но не изменено автоматически.

### Критерии для будущего ТЗ и повторной UAT-проверки

Проверить создание TYPE с обеими категориями; совместимые и несовместимые номера для каждого TYPE; смену TYPE у VEH; пустую категорию/REVIEW; номер с латинскими двойниками; уникальность; сохранность неизменных полей/версии/истории; миграционную совместимость и случай VEH без TYPE после отдельного решения. Обязательна серверная проверка, не только подсказка фронтенда.
