# CODEX ARM2-ID-001 — постоянные ID, только механизм

**Статус:** подготовлено к передаче, не запускалось. Основа: `arm2/id-001-handoff` (от принятого ARM2-BOOT-001). Сделать отдельную рабочую ветку, PR направить в `arm2/id-001-handoff`, не в `main`.

## Предметное основание
Google-конфигурация ARM 2.0, лист `03 Конфигурация`:
- `ID.R01` (частично утверждено): постоянный один предметный ID, отдельная последовательность каждого справочника, префикс + дефис + минимум шесть цифр с нулями; выдаётся автоматически, не изменяется и не переиспользуется. Не добавлять параллельный UUID предметной записи.
- `VEH.F01` (утверждено): префикс техники `VEH-`, пример `VEH-000001`; не зависит от госномера, имени, типа или владельца.
- **Префиксы других справочников пока не согласованы.** В этом задании использовать только `VEH`. Никаких придуманных `TYPE`, `CP` и т. п.
- Не переносить данные из старой ARM 1.0; прежние формулировки `SCOPE.BASE-01`/`HANDOFF.BASE-01` о миграции действующей БД относятся к предыдущему варианту архитектуры и требуют актуализации отдельно.

## Одна цель
Реализовать изолированный сервис выдачи следующего устойчивого ID вида `VEH-000001`, `VEH-000002`, … для будущего справочника техники. **Не** создавать сам справочник или карточки.

### Обязательные свойства
1. Постоянный счётчик в PostgreSQL, **не** `MAX(id)+1` и **не** переменная памяти процесса; безопасен при двух параллельных вызовах.
2. Номер не выдаётся повторно после удаления записи или отката незавершённой операции. Пропуски номеров допустимы; заново использовать их нельзя.
3. Вызов из существующей БД рабочего пространства через штатный `Db`/SQLAlchemy session; никаких соединений к БД старой ARM 1.0. Между базами разных рабочих пространств счётчики могут начинаться независимо — окончательное определение глобальной области уникальности согласуется перед внедрением в реальные справочники.
4. Формат: `VEH-` + порядковый десятичный номер с минимум 6 разрядами; не обрезать после 999999. Начиная с `VEH-000001`.
5. Не принимать произвольный префикс от пользователя или API; разрешён только явно зарегистрированный `VEH`.
6. Возвращаемая строка станет **единственным предметным ключом** будущей карточки; дополнительный скрытый UUID не вводить.
7. Не создавать HTTP endpoint генерации номера: ID выдаётся только при внутренней операции создания будущей записи. Сейчас API возвращает прежний bootstrap status.
