| Требование | Реализация |

Единственная новая миграция: **0070 после 0069**. Она требует пустой CP, не угадывает тип и не удаляет данные. Downgrade с CP/ORG отказывается от потери новых данных. Предыдущие миграции не изменены. Исторические тесты выполняют переходы на конкретных старых ревизиях с соответствующими SQL-фикстурами, не вызывая современный CP API на старой схеме.

## Команда reset и границы

На хосте целевого Docker, после отдельного разрешения на реальный reset:

```sh
python backend/tools/arm2_uat_reset.py --project arm2-ubuntu-uat-r2
python backend/tools/arm2_uat_reset.py --project arm2-ubuntu-uat-r2 --execute --confirm-project arm2-ubuntu-uat-r2
```

Первая команда только строит и проверяет план. Вторая останавливает только выбранные R2 HTTP-сервисы, повторно сверяет идентичность ресурсов и выполняет очистку. Неуспешная очистка оставляет R2 HTTP offline для повторного запуска той же команды. Журнал и quarantine обеспечивают восстановление между SQL/FILE фазами. Контейнеры, тома, VM, пользователи, bootstrap, схема, Alembic и последовательности не удаляются.

Host-команда проверяет имя проекта, сервисы, эксклюзивность томов, внутреннюю сеть, отсутствие опубликованного PostgreSQL, APP_ENV и отключённые интеграции. SQL-модуль дополнительно проверяет DB/cluster identity, revision 0069/0070, FILE/runtime roots и принадлежность файлов. Он передаётся через stdin в временный runner существующего выбранного API image; предварительная установка новой версии не требуется. Секреты не выводятся; временный env удаляется в finally.

**На настоящей VM команда не запускалась. Docker-граница проверена unit-тестами, сам reset — на disposable PostgreSQL/FILE.** Это авторская локальная проверка, не Ubuntu UAT и не операторская приёмка. Полная регрессия и внешний CI не ожидались согласно Issue #72; приведены адресные проверки. Merge, deploy, очистка реального стенда и изменения B1/ARM1/«Метки»/DOC/REG не выполнялись.
