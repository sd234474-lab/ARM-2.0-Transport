# CODEX ARM2-TYPE-001 — предметные правила типа техники, без БД и UI

Статус: ограниченный исполнимый пакет. **Не весь справочник:** первый безопасный срез перед проектированием таблицы и интерфейса.
Репозиторий: `sd234474-lab/ARM-2.0-Transport`; база: `arm2/type-001-handoff` (содержит принятые BOOT-001 и ID-001); сделай рабочую ветку от неё и PR **в эту же базовую ветку**, не `main`.

## Подтверждённое предметное основание
Единая конфигурация ARM 2.0, `03 Конфигурация`:
- `DISC-TYPE-03`: название обязательно, непустое, свободно задаваемое; не повторять полностью одинаковое название в справочнике (проверка уникальности — на этапе БД).
- `DISC-TYPE-04`: статус определяется полнотой названия и трёх ответов. `REVIEW` — если обязательное свойство отсутствует, `CONFIRMED` — если всё заполнено; `False` — заполненный ответ, не эквивалент `None`. Никакого ручного статуса, архивности типов, Wialon-интеграции.
- `DISC-TYPE-05`: `requires_calibration` может быть явным `True/False` или отсутствующим `None`; требование не выводить из имени/code.
- `DISC-TYPE-06`: `requires_sts` на данном этапе **всегда True** и по умолчанию True. Изменение на False в текущей предметной модели запрещено, хотя статус полноты учитывает этот признак.
- `DISC-TYPE-07`: `requires_wialon` — `True/False/None`; на данный момент существующие типы требуют Wialon, но новые потенциально могут иметь False, поэтому НЕ фиксировать True в коде для любого нового типа.
- `DISC-TYPE-09` и `VER.R01`: защита версии понадобится при сохранении в БД, но не сейчас.
- `DISC-TYPE-11/12`: UI будет отдельно; не создавать технические поля code/details/source.
- `ID.R01`, `DISC-TYPE-01`: один постоянный предметный ID, но префикс типов **не утверждён**; для этого пакета ID типов не создавать и не придумывать.

## Одна задача
Реализовать **чистые предметные функции** для будущего справочника типов техники, чтобы последующий этап БД и интерфейса вызывал их без повторного анализа решений.

### Обязательные функции (рекомендуемые сигнатуры; при несовместимости объяснить)
Создай `backend/app/arm2/vehicle_type_rules.py`:
- `normalize_type_name(name: str) -> str`: обрезка крайних пробелов, отказ для пустого/пробельного названия. Не выдумывать ограничение длины и дополнительные правила нормализации. Дубликаты проверяются позже на уровне БД; не считать, что функция проверила уникальность.
- `normalize_type_requirements(requires_sts: bool | None = True, requires_calibration: bool | None = None, requires_wialon: bool | None = None)` или эквивалент: нормализует строго допустимые tri-state значения, СТС по умолчанию True, явный False запрещён с понятным исключением. Не превращать `None` в False для calibration/wialon. Не принимать 0/1 или строки за bool, если используется простая Python-функция.
- `type_status(name: str, requires_sts: bool | None, requires_calibration: bool | None, requires_wialon: bool | None) -> str`: возвращает только `REVIEW` или `CONFIRMED`. Не объявлять `INCOMPLETE`/`INACTIVE` предметными статусами типов. Вызов с явно запрещённым СТС=False должен быть отклонён, а не автоматически подтверждён.
- Отдельно документируй в docstring границы этих функций, включая будущую проверку уникальности имён.

Создай `backend/tests/test_arm2_vehicle_type_rules.py` с точечными тестами:
1. Полностью заполненный тип получает CONFIRMED, в том числе `requires_calibration=False` и `requires_wialon=False`.
2. Пустой ответ в любом из двух допускающих None признаков приводит к REVIEW.
3. Название из пробелов отклоняется, краевые пробелы убираются.
4. `requires_sts` по умолчанию True, явный False отклоняется.
5. Недопустимые строки/числа вместо bool отклоняются.
6. Изменение названия/ответа меняет результат только по полноте, не по конкретной категории машины.
