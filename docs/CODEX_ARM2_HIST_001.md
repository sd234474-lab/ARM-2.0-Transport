### Предметная модель события
Создать `arm2_history_events` для независимой ARM 2.0 (НЕ использовать старый Transport MAX `Audit`, у которого `object_id` числовой).

Минимальные явные поля:
- `event_id`: технический идентификатор **события** (внутренняя identity BIGINT PK; не новый предметный ID карточки).
- `object_type`: непустой строковый код вида объекта, например `TYPE` или `VEH`; для пакета разрешить только явно зарегистрированные типы, не принимать произвольную пользовательскую строку.
- `object_id`: постоянный строковый предметный ID, например `TYPE-000001`; проверять согласованность префикса с `object_type` (для TYPE/VEH). Никаких числовых ID предметных записей.
- `operation`: непустой код действия, минимум `CREATED`, `UPDATED`; не утверждать предметную таксономию удаления, импорта и прочих будущих операций без отдельного пакета.
- `occurred_at`: отметка времени с часовым поясом и server default CURRENT_TIMESTAMP, не требовать времени клиента.
- `actor_kind`: непустой тип инициатора (человек/система) и `actor_id`: реальный, непустой строковый идентификатор инициатора; отсутствие человека отражать действительным системным субъектом, не вымышленным оператором.
- `source`: непустая строка происхождения/канала события, без искусственного жёсткого перечня кодов до решений по импорту.
- `correlation_id`: необязательный текстовый идентификатор операции/пакета для объединения связанных событий; пустую строку не выдавать за ID.
- `version_before`, `version_after`: nullable положительные целые; для CREATED expected before null, after 1; для UPDATED реальные номера версий. Не менять версию самой карточки из журнала.
- `changes`: структурированное JSONB **детальное описание** фактических изменений по полям `{field: {before: ..., after: ...}}`. Отличать `null` от `false`, хранить точные допустимые примитивные значения. Для CREATED отражать первоначальные разрешённые поля, before=null; для UPDATE — только реально изменённые поля. Уточнение: значения создаваемой записи, которые действительно равны null, должны оставаться null. Модель/формат должен сохранять возможность расширения для событий изменения связей и документов в следующих пакетах, **без** добавления фиктивных предметных полей сейчас.
- `related_objects`: JSONB массив ссылок `{object_type, object_id, relation}` — необязательный, по умолчанию пустой; ссылки не считать доказательством существования иных объектов. Типы ссылок с полноценной семантикой будут определяться по процессам, не вводить фиктивных ссылок.

Индексы: `(object_type, object_id, occurred_at, event_id)` для входа из карточки и хронологии; индекс по `correlation_id` при реальной необходимости, не строить множество преждевременных индексов.

### Требования к внутреннему API записи
- `append_history_event(db: Session, *, object_type, object_id, operation, actor_kind, actor_id, source, changes, version_before=None, version_after=None, correlation_id=None, related_objects=None)` или прозрачный равнозначный контракт.
- Данные события передаются **уже очищенными** предметным слоем. Но **не делать универсальный сбор/сериализацию `row.__dict__`, request body, произвольных JSON, ORM или вложений**. На этом этапе ограничить `changes` явно зарегистрированным белым списком полей для `TYPE`: `name`, `requires_sts`, `requires_calibration`, `requires_wialon`, `status`, `version`. Для `VEH` пока нет согласованной схемы полей: инфраструктура распознаёт тип и постоянный ID, но не принимает содержательные изменения VEH до регистрации разрешённых полей.
- Любые неразрешённые поля (например `password`, `token`, `details`, `secret`, `photo_bytes`) — отказ до записи; не достаточно одного простого списка запрещённых слов. Значения `changes` для TYPE — `str`/`bool`/`int`/`None` по известному полю и запрещать вложенные коллекции/bytes; `version` только положительные целые. Не включать PII в произвольный контекст; здесь такого поля вообще нет.
- Сервис **только `add`+`flush`, без `commit`, без `rollback` на успешном пути, без своей независимой сессии**; вызывающий код отвечает за транзакцию и обязан записать изменение предметной сущности и историю в одной сессии. Продемонстрировать тестом реальный атомарный `commit` и `rollback`.
- События истории не разрешается обновлять и удалять **через сервис**; сделать доступной только операцию добавления. Прямые изменения таблицы привилегированным SQL и законодательная политика удаления требуют отдельного решения: не утверждать, что защита от DBA или физическое бессрочное хранение реализованы.
- Проверять базовые требования `NOT NULL`/`CHECK` на уровне PostgreSQL, явно сохранить пространственную независимость: таблица создаётся штатной миграцией в текущей целевой базе (в мультиорганизационной конфигурации отдельная БД рабочего пространства). Если организация/глобальная видимость требует другой охват, он будет отдельным решением; не делать глобальную агрегацию из tenant DB.
- Не добавлять события реальных операций в этом пакете: для пользовательского CRUD обязательно отдельное подключение автора/источника, прав, адаптера ошибок и проверка атомарности.
